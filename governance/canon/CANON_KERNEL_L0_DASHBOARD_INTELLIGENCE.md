# CANON — Kernel Dashboard Intelligence

**Status:** Constitutional
**Scope:** Financial interpretation layer
**Applies to:** All present and future Aequitas dashboards
**Depends on:** Kernel L0 accounts only

---

## 1. Purpose of This Canon

This Canon defines **how financial truth may be interpreted**, not how it is stored.

The Kernel defines **what is true**.
This Canon defines **what may be inferred**.

No rule in this Canon may:

* alter data,
* generate accounting entries,
* override user intent,
* or replace human judgment.

The dashboard is an **observer**, never an actor.

---

## 2. Foundational Principle

> The dashboard may explain reality.
> It may never decide reality.

All metrics are:

* derived,
* reversible,
* explainable,
* and non-authoritative.

If a metric cannot be explained using only Kernel L0 accounts, it is forbidden.

---

## 3. Metric Classification Invariant

All dashboard metrics **must belong to exactly one of the following classes**:

1. **Core Metrics** — survival and immediacy
2. **Advanced Metrics** — operational efficiency
3. **Diagnostic Metrics** — truth and risk detection
4. **Simulations** — hypothetical exploration

No metric may belong to more than one class.

---

## 4. Core Metrics Canon

### Definition

Core Metrics answer only one question:

> “Can this company continue operating right now?”

### Constraints

Core Metrics must:

* be understandable without accounting knowledge,
* be directly traceable to Kernel balances,
* never contradict each other.

### Required Properties

* Absolute values or simple ratios only
* No assumptions
* No projections
* No accrual interpretation

### Forbidden Behaviors

* No alerts based on projections
* No “recommendations”
* No automation triggers

### Canonical Examples

* Total Cash
* Net Revenue
* Operating Income
* Net Working Capital
* Current Ratio (kernel approximation)

If Core Metrics indicate distress, **no other class may be shown by default**.

---

## 5. Advanced Metrics Canon

### Definition

Advanced Metrics explain **how well operations are structured**.

They exist only to answer:

> “Why do the Core Metrics look this way?”

### Constraints

Advanced Metrics may:

* use ratios,
* use time comparisons,
* infer efficiency.

They may not:

* infer intent,
* imply wrongdoing,
* predict outcomes.

### Required Properties

* Must decompose into Core Metrics
* Must expose their components
* Must allow period comparison

### Forbidden Behaviors

* No standalone interpretation
* No automated judgments
* No risk labels

### Canonical Examples

* Gross Margin
* Operating Margin
* Payroll Ratio
* Operating Expense Ratio
* DSO
* DPO
* Cash Conversion Cycle (kernel version)

Advanced Metrics **require Core Metric stability** to be shown.

---

## 6. Diagnostic Metrics Canon

### Definition

Diagnostic Metrics exist to detect **misalignment between accounting appearance and economic reality**.

They answer only:

> “Is the accounting telling the truth?”

### Constraints

Diagnostic Metrics:

* may challenge profit,
* may reveal stress,
* may surface inconsistencies.

They may never:

* accuse,
* decide,
* escalate automatically.

### Required Properties

* Must include explanatory context
* Must show underlying balance movements
* Must be explicitly labeled as diagnostic

### Forbidden Behaviors

* No red/yellow/green scoring
* No ranking companies
* No triggering workflows

### Canonical Examples

* Operating Cash Flow (estimated)
* Earnings Quality Ratio
* Refund Rate
* Tax Coverage Ratio
* Tax Drift Indicator
* Depreciation Intensity
* Asset Intensity Ratio

Diagnostic Metrics **must never be the first metrics shown**.

---

## 7. Simulation Canon

### Definition

Simulations are **questions posed by the user**, not statements by the system.

They ask:

> “What if?”

### Constraints

Simulations:

* must never modify real data,
* must never persist results as truth,
* must be clearly marked as hypothetical.

### Required Properties

* Explicit assumptions
* Reversible inputs
* Clear separation from actuals

### Forbidden Behaviors

* No default activation
* No automatic suggestions
* No implied advice

Simulations exist outside the metric hierarchy.

---

## 8. Interpretation Boundary Rule

The system may:

* explain relationships,
* show comparisons,
* highlight deltas.

The system may not:

* tell the user what to do,
* label behavior as good or bad,
* replace professional judgment.

Any text that implies decision-making authority violates this Canon.

---

## 9. Minimal Vector Doctrine

The dashboard **must prefer fewer metrics over more metrics**.

If two metrics explain the same phenomenon:

* the simpler one prevails,
* the other must be hidden or removed.

More data is not more truth.

---

## 10. Auditability Requirement

Every metric must:

* list the Kernel accounts it uses,
* explain changes through deltas,
* be reproducible by an accountant manually.

If a metric cannot be audited, it must not exist.

---

## 11. Forward Compatibility Rule

Future modules may:

* add enriched analytics,
* add domain-specific views,
* add industry overlays.

They may not:

* alter Kernel interpretations,
* bypass this Canon,
* redefine metric classes.

This Canon is immutable.

---

## 12. Canon Closing Statement

The dashboard is not intelligence.
It is **clarity**.

It does not optimize.
It **reveals tradeoffs**.

It does not decide.
It **respects the human**.
